# Task 9 & 10 — dashboard data layer, StatCard / SectionStrip / BarChart

## The sales trend key is `trend7`, not `trend`

**What:** `buildSalesSection` returns `{ today, thisMonth, trend7 }`. Both the plan's Task 9 Step 1
summary and the design brief (§3, line 275: "last 7 days from `sales.trend`") call it `trend`.
Reading `sections.sales.trend` yields `undefined` and an empty chart, with no error anywhere.

**Evidence:** `../Backend/src/services/dashboard/sales.section.ts` — the return literal's third key is
`trend7:`. `features/dashboard/types.ts` types it as `trend7`.

**So what:** Task 11 must read `sections.sales.trend7.series`. The plan's own Task 11 test fixture
(plan lines 1059–1063) uses `trend`, so that fixture will not typecheck against
`DashboardSalesSection` — fix the fixture, not the type.

## Four more section fields differ from the plan's Step 1 summary

**What:** Verified every `build*Section` return object against the plan's one-paragraph summary.
Four differences beyond `trend7`:

| Section | Plan said | Backend actually returns |
|---|---|---|
| `debts` | `outstanding, overdueAmount, overdueCount, overdue[]` | …plus **`dueWithin7Days: { count, amount }`** |
| `me` | `role` (implying a name) | **`role: { id, name }`** — an object |
| `organization` | `{ id, name, logo, currency }` | …plus **`timezone`**, and `currency` is **`{ main, exchange, rate } \| null`**, not a code string |
| `stock` | `threshold` | **`threshold: number \| null`** |

**Evidence:** `../Backend/src/services/dashboard/{debts,me,organization,stock}.section.ts`, the
return literal at the bottom of each file. Everything else in the summary — `sales.today`,
`sales.thisMonth`, `mySales`, `staff`, `projects`, `team`, `announcements` as a bare array with
`author: { id, name }` — matched exactly.

**So what:** `debts.dueWithin7Days` is free data the Debts panel can show without another request.
`organization.timezone` means the Overview does not need `useSession()` for the greeting's timezone.
`organization.currency` being nullable is the real trap: there is no code to format money with when
it is `null`, so render the raw figure or a dash rather than defaulting to `"USD"`.

## Two section counts are capped upstream and are not totals

**What:** `stock.lowStockCount` / `outOfStockCount` are the *lengths of the stock report's lists*,
and those lists are already capped at 50 in `getStockReport`. A business with 300 low products
reports 50. `debts.overdueCount`, by contrast, **is** the true full count while `debts.overdue` is
capped at 10.

**Evidence:** `../Backend/src/services/dashboard/stock.section.ts` (`report.lowStock.length`, with a
comment saying "a genuine count only up to that same bound") vs `debts.section.ts` (`overdueCount`
comes from `getDebtsSummary`, not from `overdue.length`).

**So what:** Do not write "300 products are low" from `lowStockCount`; write "50+" or just the list.
For debts the opposite holds — "and N more" is correct as `overdueCount - overdue.length`.

## The permission gating is finer than the route's, and one gate is deliberately a pair

**What:** `GET /dashboard` is gated on `organization:view`, which every member holds — the route is
open to all staff. The real gating is a registry inside the service, and two entries surprised me:

- `team` needs `members:view` **and** `members:invite` together, *contradicting the design spec's own
  table*, which says `members:view` alone. The backend comment explains why: the Seller preset holds
  `members:view` (sellers need to see who recorded a sale), so gating on it alone would put `team`
  in a Seller's `available` list and break the spec's "Seller sees exactly seven keys" criterion.
- `mySales` is gated on `sales:create` — an *action* permission, not a view one. A Manager who can
  record sales therefore receives **both** `mySales` and `sales`, so the Overview must handle the
  two coexisting rather than treating them as an either/or role switch.

**Evidence:** `../Backend/src/services/dashboard.service.ts`, the `SECTIONS` array and the long
comment on the `team` entry. `docs/API-ROUTES.md` line 105 for the route-level gate.

**So what:** Never infer a section's presence from a role name, and never assume `mySales` and
`sales` are mutually exclusive. `available` is the only authority, and it can contain a key this
build predates — which is why `DashboardResponse.available` stays `string[]`.

## `trend7.series[].bucket` is a date *label*, not a timestamp

**What:** `bucket` is a formatted string — `yyyy-MM-dd` at day granularity, `yyyy-MM` at month —
produced by `walkBucketLabels`, already resolved in the business timezone server-side.

**Evidence:** `../Backend/src/services/reports/sales.report.ts:125` (`bucketFormat`) and `:207`.

**So what:** It is not an instant. Passing it to `formatDate(iso, timezone)` re-interprets a
date-only string as UTC midnight and can render the previous day west of Greenwich. Slice the label
or parse it as a local calendar date.

## The canvas and the brief disagree about the chart, and the canvas won

**What:** The brief specifies a **`DotMatrixBarChart`** — "stacked small squares on a dotted grid
(LED / dot-matrix feel)" — and the plan's Task 10 Step 3 repeats it ("the canvas's stacked look — a
column of small rounded squares"). The design canvas draws neither: artboards `1a` and `1c` both
render a **solid bar with a rounded top** (`border-radius: 6px 6px 0 0`, `max-width: 56px`) on a
**four-line horizontal grid** (`linear-gradient(to top, … 1px, transparent 1px)` at `100% 25%`).

**Evidence:** brief lines 96, 398, 467 vs `docs/design/TradeOs-UI.dc.html:1861-1866` (artboard `1a`)
and `:2184-2190` (artboard `1c`).

**So what:** Built to the canvas, per the plan's Global Constraint that the canvas is the pixel spec
at 1440. If the owner wants the dot-matrix look back, it is a change to `bar-chart.tsx` alone — the
props do not move.

## Two canvas details I could not reproduce, and one measurement conflict

**What:**
1. **Per-bar value labels.** Canvas `1c` prints the value above each bar (`showBarValues`, 11px mono).
   `BarChart` receives `series: number[]` and the agreed interface has no formatted-label prop, so
   printing them would emit `20320` where the page everywhere else says `USD 20,320.00`. Left out.
2. **The legend dot and the `…` menu** in the sales-trend header are `SectionStrip`'s `actions` slot
   content, not part of the strip — Task 11 supplies them.
3. **Artboard `1a` and `1c` disagree on three measurements**: StatCard value 26px vs **24px**, spark
   bars 3px wide / 38px tall vs **4px / 36px**, SectionStrip header padding `12px 18px` vs
   **`10px 18px`**. Built to `1c`, the in-situ Overview, which is what the acceptance criterion
   compares against; `1a` is the older specimen sheet.

**Evidence:** `docs/design/TradeOs-UI.dc.html:1826-1849` (`1a`) vs `:2130-2180` (`1c`).

**So what:** If Task 11 wants the bar values on screen, add an optional `valueLabels?: string[]` to
`BarChart` and pass pre-formatted strings — do not make the component format.

## `dashboardKeys` does not use `createQueryKeys`

**What:** Task 9's "Consumes" line names `createQueryKeys`, but `features/dashboard/keys.ts` hand-rolls
`{ all, overview() }` instead.

**Evidence:** `GET /dashboard` takes no parameters at all (`../Backend/src/routes/v1/dashboard.route.ts`
validates `query: noBodySchema`), so the generic list/detail shape would only add an empty `list({})`
segment to hash. `features/auth/keys.ts` made the same call for the same reason and documents it.

**So what:** `dashboardKeys.all` is still a prefix of `overview()`, so
`invalidateQueries({ queryKey: dashboardKeys.all })` after a sale or a payment reaches the Overview.
Nothing downstream changes.
